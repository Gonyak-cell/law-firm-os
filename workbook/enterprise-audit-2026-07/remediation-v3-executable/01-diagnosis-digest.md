SUMMARY: The server-side matter opening path is fully functional: after issuing a clearance token through the live intake ledger chain (conflict-check -> clear decision -> approved engagement -> clearance token), POST /api/matters/openings returned 201 and an idempotent replay returned 200 — directly reproduced on a fresh boot at port 4191 as jwsuh@amic.kr. The P0 defect is in the web client: (1) normalizeMatterOpeningPayload in apps/web/src/data/apiClient.js force-rewrites clearance_token.tenant_id to MATTER_TENANT_ID (tenant_rp05_synthetic) while the UI issues clearance tokens only under CRM_INTAKE_TENANT_ID (tenant_cmp_g6_synthetic), so the server's ledger lookup misses and the kernel throws "Matter opening clearance token was not issued by Intake ledger" -> 400 MATTER_API_VALIDATION_ERROR; (2) MatterOpeningWizard requires the user to hand-type all 10 fields including clearance_token_id with no wiring to any issued token, so no wizard submission can ever reference a ledger token under rp05. The alternate ClientsSurface path (openMatterFromIntakeClearance, which preserves the issued token's tenant_id) succeeds live with 201 — cross-tenant is tolerated because issued tokens carry owner_module:"intake". A compounding diagnosability defect: handleMatterOpening passes `message: error.message` but errorResponse only emits `extra.safe_message`, so every 400 body is opaque (which is why the audit could not record the failing condition). Conflict-clearance enforcement itself is intact and must not be touched.
