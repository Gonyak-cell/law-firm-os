## 1. 문서 목적

이 문서는 People v2의 로컬 소스 구현 완료와 외부 시스템 개통, 운영 배포,
실사용 승인을 분리해 기록한다. 로컬 테스트나 CI 통과만으로 Microsoft 365,
은행, 세무·4대보험, 급여명세서 전달 등 외부 서비스가 실제 연결되었다고
판정하지 않는다.

출시 후보에 포함하는 기준 자료는 아래와 같다.

- `.omo/plans/goal.md`
- `.omo/plans/people-goal-remediation-20260731.md`
- `.lazyweb/design-improve/people-tuw-detailed-plan-v2-2026-07-30/report.html`
- `artifacts/people-v2/PEO-TUW-001/implementation-ledger.json`

커밋 전 최종 검증에 사용한 `.omo/evidence/*`와
`artifacts/people-v2/implementation-completion-receipt.json`은 로컬 작업 경로와
원시 테스트 로그를 포함한 작업 증거다. 이 자료는 PR 출시 파일로 사용하지 않고,
PR CI 결과와 병합 커밋 SHA를 저장소에서 재현 가능한 출시 증거로 사용한다.

## 3. 외부 연동 조건 목록

### EXT-01 Microsoft 365 일정

- 상태: `OPEN`
- 필요한 조건:
  - Microsoft 365 테넌트 관리자 동의
  - 운영용 토큰 보관소와 키 회전·폐기 절차
  - 실제 Microsoft Graph 일정 어댑터
  - 구성원 계정과 Outlook 계정의 검증된 연결
- 완료 증거:
  - 테넌트, 승인 범위, 승인자, 승인 시각이 적힌 동의 기록
  - 비밀값을 제외한 토큰 보관·회전 설정 확인서
  - 운영과 동일한 환경에서 필수 참석 회의만 `오늘 할 일`에 들어가고 선택 참석
    회의는 일정에만 남는 실제 계정 검증 결과
  - 동의 철회, 만료 토큰, 다른 테넌트, 계정 연결 불일치가 안전하게 차단되는 결과
- 미충족 시 동작: Outlook 연동을 사용할 수 있다고 표시하지 않고 기능을
  비활성화하거나 `연결 필요` 상태로 유지한다.

### EXT-02 채용 자료와 보상 조건 권한

- 상태: `OPEN`
- 필요한 조건:
  - 실제 채용 자료 원본 시스템
  - 지원자 개인정보 수집·이용 동의 기록
  - Vault 문서의 열람·보존 권한
  - 보상 조건을 확정할 담당자 권한
- 완료 증거:
  - 자료별 원본 위치, 동의 기록, 접근 권한, 보존 기간
  - 권한이 없는 사용자의 검색·열람·전환 차단 결과
  - 채용 전환과 보상 조건 확정의 승인·감사 기록
- 미충족 시 동작: 샘플 자료를 운영 자료로 대체하지 않으며, 권한이 필요한
  작업은 검토 대기 또는 비활성 상태를 유지한다.

### EXT-03 실제 급여 지급

- 상태: `OPEN`
- 필요한 조건:
  - 실제 은행 또는 지급 서비스 계약·운영 설정
  - 중복 지급을 막는 요청 키와 지급 결과 확인 절차
  - 계좌 정보 보호와 추가 인증
- 완료 증거:
  - 테스트 계좌의 소액 지급 또는 제공자가 인정하는 운영 검증 기록
  - 성공·실패·재시도·중복 요청별 제공자 확인서
  - 내부 지급 건과 은행 결과의 대사 기록
- 미충족 시 동작: 지급 파일·배치 생성 결과를 실제 송금 완료로 표시하지 않는다.

### EXT-04 세무·4대보험 신고

- 상태: `OPEN`
- 필요한 조건:
  - 실제 세무·4대보험 신고 서비스와 운영 권한
  - 신고 제출, 접수, 반려, 정정 결과를 검증하는 연결
- 완료 증거:
  - 실제 제공자가 발행한 접수·반려·정정 확인서
  - 중복 제출 방지와 재시도 결과
  - 신고 원본, 제출 내용, 결과의 체크섬 연결
- 미충족 시 동작: 내부 계산이나 파일 생성을 관공서 접수 완료로 표시하지 않는다.

### EXT-05 급여명세서 전달

- 상태: `OPEN`
- 필요한 조건:
  - 실제 명세서 전달 서비스
  - 수신자 확인, 전달 실패, 재전송, 접근 만료 처리
  - 민감 정보가 로그·알림에 노출되지 않는 설정
- 완료 증거:
  - 실제 전달 서비스의 전송·실패·재전송 확인서
  - 잘못된 수신자, 권한 없음, 만료 링크의 차단 결과
- 미충족 시 동작: 문서 생성과 전달 완료를 분리해 표시한다.

### EXT-06 법률 검토 승인

- 상태: `OPEN`
- 필요한 조건:

- 완료 증거:
  - 검토 대상 버전, 적용 기간, 검토자, 승인·보완 의견, 승인 시각이 포함된 기록
  - 법령 또는 내부 규정 변경 시 재검토 기준
- 미충족 시 동작: 법률 검토가 필요한 규칙은 `검토 필요` 상태를 유지하며
  운영 확정값으로 취급하지 않는다.

### EXT-07 동일 소스 패키징·배포·로그인 검증

- 상태: `OPEN`
- 필요한 조건:
  - 승인된 PR이 병합된 정확한 `main` 커밋 SHA
  - 같은 SHA에서 만든 API, 웹, 데스크톱 패키지
  - 데이터베이스 변경 사전 연습, 백업, 복구 기준
  - 환경·작업자·시각·아티팩트 해시가 포함된 배포 기록
  - 로그인한 실제 사용자 화면 검증
- 완료 증거:
  - `main` 병합 SHA와 각 배포 아티팩트 SHA-256의 연결
  - 스테이징 및 운영 API·웹 배포 기록
  - 데스크톱 패키지 설치·재시작·로그인 검증 기록
  - People 개요, 구성원 `오늘`, `담당 사건`, 일정·업무량, 권한 없음,
    데이터 없음, 오류 상태의 운영 화면 증거
  - 운영 스모크와 관찰 결과
- 미충족 시 동작: 로컬 미리보기, CI 빌드, API 배포 중 하나만으로 전체 배포 또는
  실사용 완료를 주장하지 않는다.

## 4. 조건을 닫는 공통 규칙

각 조건은 다음 정보가 모두 있어야 `CLOSED`로 바꿀 수 있다.

1. 정확한 환경과 테넌트
2. 검증한 병합 커밋 SHA와 배포 아티팩트 해시
3. 작업자와 승인자
4. 검증 시각과 재현 가능한 절차
5. 성공 결과와 의도적인 실패·권한 거부 결과
6. 비밀값을 제외한 제공자 확인서 또는 운영 기록
7. 장애 시 비활성화·복구 기준

로컬 목, 정적 설명서, 테스트 전용 어댑터, 화면의 성공 문구만으로 조건을
닫지 않는다. 조건이 일부만 충족되면 `IN_REVIEW`로 기록하고 누락된 증거를
명시한다.

## 5. 커밋부터 운영 확인까지의 순서

### R0 출시 범위 고정

1. People v2 소스, 테스트, 마이그레이션, 계획·검증 자료의 포함 목록을 확정한다.
2. 기존 `artifacts/manual-qa/*` 변경처럼 이번 작업과 관계없는 생성 파일은 제외한다.
3. `apps/web/src/styles.css`, `apps/api/src/hrx-runtime-context.js`, 급여 저장소처럼
   변경량이 큰 공용 파일은 변경 단위별로 People 범위인지 재확인한다.
4. 비밀값, 로컬 데이터베이스, 설치 산출물, 임시 링크가 없는지 다시 검사한다.

### R1 출시 후보 커밋

1. 현재 작업 내용을 기능 브랜치에 커밋한다.
2. 현재 `origin/main`이 기준 커밋보다 2개 커밋 앞서 있으므로, 커밋 뒤 최신
   `origin/main` 위로 기능 커밋을 재배치한다.
3. 충돌 해결 뒤 소스 지문과 완료 영수증을 새 커밋 기준으로 다시 만든다.
4. 전체 회귀, 타입 검사, 빌드, 마이그레이션 검증, 시각 검증을 다시 수행한다.

### R2 푸시와 PR

1. 재검증한 기능 브랜치를 원격에 푸시한다.
2. 먼저 Draft PR을 만들고 범위, 외부 연동 조건, 테스트 결과, 롤백 기준을 적는다.
3. PR CI에서 최소한 다음 검증을 통과한다.
   - `.github/workflows/hrx-production-rollout.yml`
   - `.github/workflows/json-postgres-program-security.yml`
   - 저장소의 필수 보안·권한·마이그레이션 검사
4. CI 성공과 사람의 코드 검토를 별도 기록한다. CI는 배포나 실사용 승인이 아니다.

### R3 `main` 병합

1. 필수 CI와 코드 검토가 끝난 PR만 `main`에 병합한다.
2. 병합 직후 정확한 병합 SHA를 기록한다.
3. 병합 SHA에서 출시 아티팩트와 스테이징 배포물을 새로 만든다. 기능 브랜치에서
   미리 만든 패키지를 운영에 재사용하지 않는다.

### R4 스테이징

1. 같은 병합 SHA의 API와 웹을 운영과 같은 설정의 스테이징에 배포한다.
2. Matter 마이그레이션 `003..005`와 HRX 마이그레이션 `033..048`을 대상으로
   사전 연습, 비파괴 확인, 백업·복구 확인을 먼저 수행한다.
3. 로그인한 계정으로 People 개요, 구성원 상세, 담당 사건, 오늘 할 일,
   분 단위 일정, 권한 거부, 데이터 없음·오류 상태를 검증한다.
4. 외부 연동 조건이 열려 있는 기능은 비활성 또는 안전 차단 상태인지 확인한다.
5. 보안 검토와 사용자 인수 검사를 마친 뒤 사람이 운영 진행 여부를 결정한다.

### R5 운영 배포

1. 배포 직전 이전 운영 SHA, 데이터베이스 백업, 기능 비활성화 방법을 확인한다.
2. API Lambda와 웹 배포를 각각 수행하고 같은 병합 SHA에 연결한다.
   - API 운영 대상: `matter-lawos-api-prod`
   - AWS 프로필/리전: `matter-prod-deploy-admin`, `ap-northeast-2`
   - 웹 운영 확인 대상: `https://d2mthcc8vp3cr2.cloudfront.net`
3. 데스크톱은 웹·API 배포와 별도 패키지로 만들고 설치, 재시작, 로그인까지
   검증한다.
4. `npm run hrx:production:smoke`와 로그인 상태 핵심 흐름을 확인한다.
5. 오류율, 지연, 권한 거부, 감사 기록, 외부 제공자 실패를 관찰하고 결과를 남긴다.

현재 GitHub Actions의 HRX 작업은 테스트와 검증만 수행한다. AWS, 웹, API,
데스크톱 배포는 자동으로 실행되지 않으므로 초록색 CI를 배포 완료로 해석하지 않는다.

## 6. 중단 및 복구 기준

다음 중 하나라도 발생하면 운영 확대를 중단한다.

- 테넌트 또는 Matter 권한 경계 위반
- 급여·계좌·후보자·일정 개인정보 노출
- 추가 인증 우회 또는 서로 다른 인증 목적의 재사용
- 마이그레이션 건수·체크섬 불일치
- 중복 지급·중복 신고 가능성
- API 5xx 급증, 로그인 불가, People 핵심 화면 미표시
- 배포 SHA와 검증 SHA 불일치

복구 순서는 영향을 받는 People·외부 연동 기능 비활성화, 감사 자료 보존,
직전 검증 SHA로 애플리케이션 복구, 필요 시 검증한 백업 복원, 데이터 건수·해시
대조, 회귀·운영 스모크 재실행 순서다. 데이터베이스 변경이 이미 적용된 경우에는
검토되지 않은 역방향 SQL을 즉석 실행하지 않는다.
